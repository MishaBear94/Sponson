A recipe is a verified [`http`](/reference/plan-format#the-generic-http-adapter) spec for one operation of one provider,
shipped with Sponson: the line names it and fills in its params, and the requests, envelopes, ids and drift rules
come from the recipe. Everything the generic adapter guarantees holds unchanged (intents before creates, idempotent
apply, drift by hash, destroy only what Sponson created). Why and how: [ADR 0020](/contributing/adr/0020-recipes).

```yaml
providers:
  http:
    cloudflare: { recipe: cloudflare }   # optional: the recipe's API defaults; override base_url, auth, headers here
changes:
  - id: preview_dns
    adapter: http
    op: resource                         # the recipe's kind: resource or list_item
    recipe: cloudflare.dns_cname
    zone_id: 023e105f4ecef8ad9ca31a8372d0c353
    name: "${ctx.scope}.preview.example.com"
    target: preview-host.example.net
```

- `recipe: <provider>.<op>` picks the operation; `api` defaults to `<provider>`, and so does its block under
  `providers.http`: write the block only to override `base_url`, `base_url_env`, `auth`, `headers` or `encoding`.
- Every other key of the line is one of the recipe's params. Values are literals, `${ctx.*}`, `{ from }`,
  `{ secret }` or `{ keep: true }`, as anywhere in a plan. An unknown param, a missing required one or a value of
  the wrong type is `PARAM_INVALID` naming it, before any request; an unknown recipe or op lists the known ones.
- `destroy: keep` leaves what the line made in place when the scope is destroyed.
- Identity: the ledger records the API block as resolved (base URL, credential variable, headers, encoding) and the
  keys and record ids of the expanded requests, never the recipe's text. A line written by hand with the same
  values is the same resource, and a new Sponson version whose recipe changes only its docs, params or assumptions
  re-identifies nothing.

Every op below is tested by `scenarios/recipes.test.ts` against the local fake cloud (create, idempotent re-apply,
drift, destroy), and live with `pnpm test:live` when its credential and the `SPONSON_LIVE_*` variables its recipe
names are set.

| API default | Value |
|---|---|
| `base_url` | `https://api.cloudflare.com/client/v4` |
| `base_url_env` | `CLOUDFLARE_API_URL` |
| Credential | `CLOUDFLARE_API_TOKEN` (bearer) |

Assumptions:

- **CF1** (verified, [source](https://developers.cloudflare.com/api/resources/dns/subresources/records/methods/create/)): Records are created with `POST /zones/{zone_id}/dns_records` (`type`, `name`, `content`, `ttl`, `proxied`, `comment`), authenticated with an API token as `Authorization: Bearer` that has DNS Write on the zone.
- **CF2** (verified, [source](https://developers.cloudflare.com/api/resources/dns/subresources/records/methods/list/)): `GET /zones/{zone_id}/dns_records` answers `{ result: [...] }` and filters by `type` and `name.exact` (names compare case-insensitively).
- **CF3** (verified, [source](https://developers.cloudflare.com/api/resources/dns/subresources/records/methods/get/)): Single-record answers (create, details, update) carry the record under `result`, with its `id`.
- **CF4** (verified, [source](https://developers.cloudflare.com/api/resources/dns/subresources/records/methods/delete/)): `PATCH /zones/{zone_id}/dns_records/{id}` updates a record; `DELETE` on the same path removes it permanently.
- **CF5** **(unverified)**: A PATCH needs `name` and `type` alongside the changed fields (the edit schema does not mark them optional), so every update sends both.
- **CF6** **(unverified)**: The API returns `name` lower-cased as the full name and `content` as written, so `name` must be given lower-case and fully qualified, or every plan finds no record and tries to create one.
- **CF7** **(unverified)**: A proxied record reports `ttl: 1` (automatic) whatever was sent, so `ttl` other than 1 with `proxied: true` shows as drift on every plan.
- **CF8** (verified, [source](https://developers.cloudflare.com/api/resources/dns/subresources/records/methods/create/)): A CNAME cannot share its name with another record, so name and type identify it within the zone and a filtered list holds at most one, on its first page.

### `cloudflare.dns_cname`

**DNS CNAME record** (`http.resource`). A CNAME record in a zone, such as `pr-42.preview.example.com` pointing at the preview deployment's host. Located by name and type; a console edit of its target, proxying, TTL or comment is drift.

Covers: `cloudflare-dns` in [the coverage matrix](/reference/coverage#coverage-matrix). Outputs: `id`, `hostname`.

| Param | Type | Required | Default | Meaning |
|---|---|---|---|---|
| `zone_id` | string | yes | — | The zone's id (32 hex characters, on the zone's Overview page). Matches `^[0-9a-f]{32}$`. |
| `name` | string | yes | — | The record's full name, lower-case, zone included. Matches `^[a-z0-9*_.-]+$`. |
| `target` | string | yes | — | The host the name points at (the record's `content`). |
| `proxied` | boolean | no | `false` | Whether Cloudflare proxies the traffic. |
| `ttl` | integer | no | `1` | TTL in seconds (60–86400), or 1 for automatic. |
| `comment` | string | no | — | A note on the record; no effect on DNS. |

```yaml
# under changes: (no provider block needed)
- id: dns_cname
  adapter: http
  op: resource
  recipe: cloudflare.dns_cname
  zone_id: 023e105f4ecef8ad9ca31a8372d0c353
  name: ${ctx.scope}.preview.example.com
  target: preview-host.example.net
  comment: Managed by Sponson
```

What the line expands into: the [`http.resource`](/reference/plan-format#http-resource) params, `{ param: <name> }` standing for a param's value and `{<name>}` in a path for its URI-encoded value.

```yaml
find:
  path: /zones/{zone_id}/dns_records?type=CNAME&name.exact={name}
  list_path: /result
  match:
    type: CNAME
    name: { param: name }
create:
  path: /zones/{zone_id}/dns_records
update:
  method: PATCH
  path: /zones/{zone_id}/dns_records/{id}
  body:
    type: CNAME
    name: { param: name }
delete:
  path: /zones/{zone_id}/dns_records/{id}
item_path: /result
fields:
  content: { param: target }
  proxied: { param: proxied }
  ttl: { param: ttl }
  comment: { param: comment }
outputs:
  hostname: /name
```

Assumptions:

- **ST1** (verified, [source](https://docs.stripe.com/api/authentication)): The API takes a secret or restricted key as `Authorization: Bearer` (besides Basic), and request bodies form-encoded with bracketed nesting (`metadata[k]=v`, `enabled_events[0]=x`).
- **ST2** (verified, [source](https://docs.stripe.com/keys)): Test-mode keys start with `sk_test_` / `rk_test_`, live-mode keys with `sk_live_` / `rk_live_`; objects of one mode are invisible to the other. The recipe refuses the live prefixes (`refuse_credential`) unless `SPONSON_STRIPE_ALLOW_LIVE=1`.
- **ST3** **(unverified)**: Organization keys (`sk_org_…`) and platform-managed keys do not carry the mode in their prefix, so they are not refused: use a test-mode secret or restricted key for previews.
- **ST4** (verified, [source](https://docs.stripe.com/api/idempotent_requests)): Every v1 `POST` accepts an `Idempotency-Key` (up to 255 characters, kept at least 24 hours); a retry with the same key returns the saved answer, and different parameters under one key are an error.
- **ST5** (verified, [source](https://docs.stripe.com/api/webhook_endpoints/create)): `POST /v1/webhook_endpoints` takes `url`, `enabled_events` (`['*']` for all), `description`, `metadata` and `api_version`, and answers the endpoint with its signing `secret` populated.
- **ST6** (verified, [source](https://docs.stripe.com/api/webhook_endpoints/list)): `GET /v1/webhook_endpoints` (`limit` 1–100) answers `{ data: [...], has_more }` whose endpoints carry `url`, `enabled_events`, `description` and `metadata` but no `secret`: the secret exists only in the create's answer, hence the `once` output.
- **ST7** (verified, [source](https://docs.stripe.com/development/dashboard/webhooks)): An account has at most 16 webhook endpoints, so one list page of 100 holds them all, and at most 16 previews (minus the account's own endpoints) can have one at a time.
- **ST8** (verified, [source](https://docs.stripe.com/api/webhook_endpoints/update)): `POST /v1/webhook_endpoints/{id}` updates `url`, `enabled_events`, `description`, `metadata` and `disabled` in place (the secret is not rotated); `DELETE` on the same path removes the endpoint.
- **ST9** **(unverified)**: The API returns `url`, `enabled_events` and `description` as they were written, `enabled_events` in the order sent, so an unchanged endpoint hashes the same on every plan.
- **ST10** (verified, [source](https://docs.stripe.com/api/products/create)): `POST /v1/products` takes a client-chosen `id` (unique among the account's products), `name`, `description` and `active`; `GET /v1/products/{id}` retrieves it; `POST /v1/products/{id}` updates it.
- **ST11** (verified, [source](https://docs.stripe.com/api/products/delete)): A product can be deleted only while it has no prices, and prices are never deleted, so the recipe archives a product (`active: false`) instead of deleting it.
- **ST12** **(unverified)**: An archived product is still returned by `GET /v1/products/{id}`, and its id stays taken: re-applying a destroyed scope finds it and reactivates it as an adopted object, which a later destroy leaves active.
- **ST13** (verified, [source](https://docs.stripe.com/api/prices/create)): `POST /v1/prices` takes `product`, `currency`, `unit_amount`, `recurring[interval]`, `nickname`, `lookup_key` and `transfer_lookup_key` (which moves the lookup key from the price holding it to the new one).
- **ST14** (verified, [source](https://docs.stripe.com/api/prices/list)): `GET /v1/prices` lists active prices by default, filters by up to 10 `lookup_keys` and by `active`, and answers `{ data: [...] }`.
- **ST15** (verified, [source](https://docs.stripe.com/api/prices/update)): A price's amount, currency and interval cannot change after creation; `POST /v1/prices/{id}` updates `active`, `nickname`, `lookup_key` and `metadata`. There is no delete: the recipe archives (`active: false`).
- **ST16** (verified, [source](https://docs.stripe.com/api/coupons/create)): `POST /v1/coupons` takes a client-chosen `id`, `name`, `percent_off` or `amount_off` with `currency`, `duration` (`once`, `repeating`, `forever`) and `duration_in_months`.
- **ST17** **(unverified)**: `GET /v1/coupons/{id}` retrieves a coupon, `POST /v1/coupons/{id}` updates its `name` and `metadata` only (the discount is fixed), and `DELETE /v1/coupons/{id}` deletes it, after which its id may be used again.
- **ST18** **(unverified)**: Stripe must reach the endpoint's URL over public HTTPS: a preview behind deployment protection (Vercel Authentication) receives no events unless it lets Stripe's requests through.

### `stripe.webhook_endpoint`

**Webhook endpoint** (`http.resource`). A test-mode webhook endpoint that sends the preview's events to its own URL, `url` + `path` (usually `{ from: web.preview_url }`). Identified by `name` in its metadata, so a new preview URL updates the endpoint in place. Its signing `secret` exists only in the answer that creates the endpoint: it is a once-only output, passed in the same run to the line that writes it (`STRIPE_WEBHOOK_SECRET` in a `vercel.env` or `netlify.env` line); later runs keep what that line holds, and `apply --recreate <line>` rotates it. Writing the secret rebuilds the preview, and a preview URL output follows the newest deploy, so the next run moves the endpoint to the rebuilt deploy's URL (in place: the secret is kept); a URL that does not change per deploy (`https://deploy-preview-${ctx.pr.number}--<site>.netlify.app`, a custom preview domain) avoids that update. A console edit of its URL, events or description is drift.

Covers: `stripe-webhook` in [the coverage matrix](/reference/coverage#coverage-matrix). Outputs: `id`, `secret` (sensitive, once-only: only in the run that creates it).

| Param | Type | Required | Default | Meaning |
|---|---|---|---|---|
| `name` | string | yes | — | The endpoint's identity, kept in its metadata (`sponson_endpoint`): unique per preview, such as `preview-${ctx.scope}`. Matches `^[A-Za-z0-9_.:/-]{1,200}$`. |
| `url` | string | yes | — | The preview's base URL, without a trailing slash: usually `{ from: <vercel.env or netlify.env line>.preview_url }`. Matches `^https://\\S*[^/]$`. |
| `path` | string | no | `/api/webhooks/stripe` | The path of the app's webhook handler, appended to `url`. Matches `^/\\S*$`. |
| `enabled_events` | list | no | `["*"]` | The event types sent to the endpoint (`['*']`: all that need no explicit selection). |
| `description` | string | no | — | A note shown in the Dashboard. |
| `api_version` | string | no | — | The Stripe API version events are rendered with (the account's default when left out); sent on create only. |

```yaml
# under changes: (no provider block needed)
- id: webhook_endpoint
  adapter: http
  op: resource
  recipe: stripe.webhook_endpoint
  name: preview-${ctx.scope}
  url: https://pr-42.preview.example.com
  enabled_events:
    - checkout.session.completed
    - customer.subscription.updated
  description: Preview webhook managed by Sponson
```

| API default | Value |
|---|---|
| `base_url` | `https://management.stytch.com` |
| `base_url_env` | `STYTCH_MANAGEMENT_API_URL` |

Assumptions:

- **SY1** (verified, [source](https://stytch.com/docs/api-reference/pwa/api/v3/redirect-urls/create-redirect-url)): The management API authenticates with HTTP Basic: a workspace management key's id as the user and its secret as the password.
- **SY2** (verified, [source](https://stytch.com/docs/api-reference/pwa/api/v3/redirect-urls/create-redirect-url)): `POST /pwa/v3/projects/{project_slug}/environments/{environment_slug}/redirect_urls` takes `url`, `valid_types` (`{ type, is_default }`, type one of LOGIN, INVITE, SIGNUP, RESET_PASSWORD, DISCOVERY) and `do_not_promote_defaults`, and answers `{ request_id, redirect_url: { url, valid_types }, status_code }`.
- **SY3** (verified, [source](https://stytch.com/docs/api-reference/pwa/api/v3/redirect-urls/get-all-redirect-urls)): `GET …/redirect_urls/all` answers `{ redirect_urls: [{ url, valid_types }], … }`: every redirect URL of the environment, unpaged.
- **SY4** (verified, [source](https://stytch.com/docs/api-reference/pwa/api/v3/redirect-urls/delete-redirect-url)): A redirect URL has no id of its own: `GET`, `PUT` (to change `valid_types`) and `DELETE` on `…/redirect_urls?url=<url>` address it by its URL.
- **SY5** (verified, [source](https://stytch.com/docs/workspace-management/pwa/limits)): A project has at most 100 redirect URLs.
- **SY6** **(unverified)**: `do_not_promote_defaults: true` on create and delete keeps a preview URL from becoming, or a deletion from changing, the environment's default for a type.
- **SY7** **(unverified)**: A `PUT` body that also carries `url` (the adapter sends the identifying field back on PUT) is accepted, and `valid_types` read back in the order and form they were written, so an unchanged URL hashes the same on every plan.
- **SY8** **(unverified)**: Each redirect URL is its own object (no shared list to rewrite), so concurrent previews need no lock.

### `stytch.redirect_url`

**Redirect URL** (`http.resource`). One redirect URL of a Stytch project environment, such as the preview's `/authenticate`, with the redirect types it is valid for (by default login and sign-up, never the default). Found by its URL; a console edit of its types is drift and is put back with a `PUT`. Destroy deletes it without promoting another URL to default.

Covers: `stytch-redirect` in [the coverage matrix](/reference/coverage#coverage-matrix). Outputs: `id`.

| `environment_slug` | string | yes | — | The environment's slug within the project (its test environment, or a custom one). Matches `^[A-Za-z0-9_-]+$`. |
| `url` | string | yes | — | The redirect URL, exactly as Stytch will receive it (`https://pr-42.preview.example.com/authenticate`). Matches `^https?://\\S+$`. |
| `valid_types` | list | no | `[{"type":"LOGIN","is_default":false},{"type":"SIGNUP","is_default":false}]` | The redirect types the URL is valid for: `{ type, is_default }` with type LOGIN, INVITE, SIGNUP, RESET_PASSWORD or DISCOVERY. |

Assumptions:

- **WO1** (verified, [source](https://workos.com/docs/reference/authkit/redirect-uri)): `POST /user_management/redirect_uris` with `{ uri }` creates a redirect URI for the environment the API key (`Authorization: Bearer sk_…`) belongs to, and answers the `redirect_uri` object (`id`, `uri`, `default`).
