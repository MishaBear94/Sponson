A recipe is a verified [`http`](/reference/plan-format#the-generic-http-adapter) spec for one operation of one provider,
shipped with Sponson: the line names it and fills in its params, and the requests, envelopes, ids and drift rules
come from the recipe. Everything the generic adapter guarantees holds unchanged (intents before creates, idempotent
apply, drift by hash, destroy only what Sponson created). Why and how: [ADR 0020](/contributing/adr/0020-recipes).

```yaml
providers:
  http:
    cloudflare: { recipe: cloudflare }   # optional: the recipe's API defaults; override base_url, auth, headers here
changes:
  - id: preview_dns
    adapter: http
    op: resource                         # the recipe's kind: resource or list_item
    recipe: cloudflare.dns_cname
    zone_id: 023e105f4ecef8ad9ca31a8372d0c353
    name: "${ctx.scope}.preview.example.com"
    target: preview-host.example.net
```

- `recipe: <provider>.<op>` picks the operation; `api` defaults to `<provider>`, and so does its block under
  `providers.http`: write the block only to override `base_url`, `base_url_env`, `auth`, `headers` or `encoding`.
- Every other key of the line is one of the recipe's params. Values are literals, `${ctx.*}`, `{ from }`,
  `{ secret }` or `{ keep: true }`, as anywhere in a plan. An unknown param, a missing required one or a value of
  the wrong type is `PARAM_INVALID` naming it, before any request; an unknown recipe or op lists the known ones.
- `destroy: keep` leaves what the line made in place when the scope is destroyed.
- Identity: the ledger records the API block as resolved (base URL, credential variable, headers, encoding) and the
  keys and record ids of the expanded requests, never the recipe's text. A line written by hand with the same
  values is the same resource, and a new Sponson version whose recipe changes only its docs, params or assumptions
  re-identifies nothing.

Every op below is tested by `scenarios/recipes.test.ts` against the local fake cloud (create, idempotent re-apply,
drift, destroy), and live with `pnpm test:live` when its credential and the `SPONSON_LIVE_*` variables its recipe
names are set.

Assumptions:

- **CF1** (verified, [source](https://developers.cloudflare.com/api/resources/dns/subresources/records/methods/create/)): Records are created with `POST /zones/{zone_id}/dns_records` (`type`, `name`, `content`, `ttl`, `proxied`, `comment`), authenticated with an API token as `Authorization: Bearer` that has DNS Write on the zone.
- **CF2** (verified, [source](https://developers.cloudflare.com/api/resources/dns/subresources/records/methods/list/)): `GET /zones/{zone_id}/dns_records` answers `{ result: [...] }` and filters by `type` and `name.exact` (names compare case-insensitively).
- **CF3** (verified, [source](https://developers.cloudflare.com/api/resources/dns/subresources/records/methods/get/)): Single-record answers (create, details, update) carry the record under `result`, with its `id`.
- **CF4** (verified, [source](https://developers.cloudflare.com/api/resources/dns/subresources/records/methods/delete/)): `PATCH /zones/{zone_id}/dns_records/{id}` updates a record; `DELETE` on the same path removes it permanently.
- **CF5** **(unverified)**: A PATCH needs `name` and `type` alongside the changed fields (the edit schema does not mark them optional), so every update sends both.
- **CF6** **(unverified)**: The API returns `name` lower-cased as the full name and `content` as written, so `name` must be given lower-case and fully qualified, or every plan finds no record and tries to create one.
- **CF7** **(unverified)**: A proxied record reports `ttl: 1` (automatic) whatever was sent, so `ttl` other than 1 with `proxied: true` shows as drift on every plan.
- **CF8** (verified, [source](https://developers.cloudflare.com/api/resources/dns/subresources/records/methods/create/)): A CNAME cannot share its name with another record, so name and type identify it within the zone and a filtered list holds at most one, on its first page.

### `cloudflare.dns_cname`

|---|---|---|---|---|
| `zone_id` | string | yes | — | The zone's id (32 hex characters, on the zone's Overview page). Matches `^[0-9a-f]{32}$`. |
| `name` | string | yes | — | The record's full name, lower-case, zone included. Matches `^[a-z0-9*_.-]+$`. |
| `target` | string | yes | — | The host the name points at (the record's `content`). |

| Credential | `GITHUB_TOKEN` (bearer) |
| `headers` | &#123;"X-GitHub-Api-Version":"2022-11-28","User-Agent":"sponson"&#125; |

Assumptions:

- **GH1** (verified, [source](https://docs.github.com/en/rest/repos/webhooks)): `POST /repos/{owner}/{repo}/hooks` creates a repository webhook from `name: web`, `config` (`url`, `content_type`, `secret`, `insecure_ssl`), `events` and `active`, answering 201 with the hook (its integer `id` and `config`), authenticated with `Authorization: Bearer <token>`.
- **GH2** (verified, [source](https://docs.github.com/en/rest/repos/webhooks)): `GET /repos/{owner}/{repo}/hooks` answers a bare array of hooks, each with `config.url`; it pages with `per_page` (at most 100) and `page`.
- **GH3** (verified, [source](https://docs.github.com/en/rest/repos/webhooks)): `PATCH /repos/{owner}/{repo}/hooks/{hook_id}` updates `config`, `events` (replacing the list) and `active`; a secret set before is removed unless the same or a new one is sent, so every update sends the config's `url` and `secret` again.
- **GH4** (verified, [source](https://docs.github.com/en/rest/repos/webhooks)): `DELETE /repos/{owner}/{repo}/hooks/{hook_id}` answers 204, and 404 when the hook is gone.
- **GH5** (verified, [source](https://docs.github.com/en/rest/repos/webhooks)): Each hook should have a unique config, and hooks may share one only when their events do not overlap. The recipe takes the URL as the hook's identity; two hooks with the same URL make `find` refuse (PARAM_INVALID) instead of guessing.
- **GH6** **(unverified)**: The secret is write-only: answers carry it masked or not at all, so it is sent on create and update but never compared, and a secret changed in the plan reaches GitHub only with the next change of a compared field. Keep it in a secret manager and reference it with `{ secret: … }`.
- **GH7** **(unverified)**: A repository has at most 100 hooks for this purpose (GitHub limits hooks per event), so the first page of `?per_page=100` holds the one `find` looks for.
- **GH8** **(unverified)**: `config.content_type` and `config.insecure_ssl` are answered as sent (`json`/`form`, the strings `"0"`/`"1"`), and `Accept: application/json` is served like `application/vnd.github+json`.
- **GH9** **(unverified)**: The token needs the repository permission Webhooks (write) or the classic `admin:repo_hook` scope; the `GITHUB_TOKEN` of GitHub Actions does not have it, so use a GitHub App token or a fine-grained token. `GITHUB_API_URL` (set by Actions) points at GitHub Enterprise Server where that is the host.

Covers: `github-webhook` in [the coverage matrix](/reference/coverage#coverage-matrix). Outputs: `id`. On destroy: deleted (`destroy: keep` on the line leaves it).

| `owner` | string | yes | — | The repository's owner (user or organization). |
| `repo` | string | yes | — | The repository's name. |
| `url` | string | yes | — | The URL GitHub delivers to; it identifies the hook in the repository. Matches `^https?://\\S+$`. |
| `events` | list | no | `["push"]` | The events that trigger a delivery (`["*"]` for all). |
| `active` | boolean | no | `true` | Whether deliveries are sent. |
| `content_type` | string | no | `json` | The payload's media type. One of `json`, `form`. |

## Svix

Recipe file: [`packages/adapters/recipes/svix.yaml`](https://github.com/MishaBear94/Sponson/blob/main/packages/adapters/recipes/svix.yaml). Verified on 2026-10-11 against:

- [Svix API reference (OpenAPI document)](https://api.svix.com/api/v1/openapi.json)
- [Svix API reference](https://api.svix.com/docs)
- [Entities overview (ids and uids)](https://docs.svix.com/overview)

| API default | Value |
|---|---|
| `base_url` | `https://api.us.svix.com` |
| `base_url_env` | `SVIX_API_URL` |
| Credential | `SVIX_AUTH_TOKEN` (bearer) |

Assumptions:

- **SV1** (verified, [source](https://api.svix.com/api/v1/openapi.json)): `POST /api/v1/app/{app_id}/endpoint` creates an endpoint from `url` (required), `uid`, `description`, `eventTypes`, `channels`, `disabled`, `metadata` and an optional `secret`, answering 201 with the endpoint (`id` `ep_…`, `uid`, `url`, …); requests carry `Authorization: Bearer <token>`.
- **SV2** (verified, [source](https://api.svix.com/api/v1/openapi.json)): `GET`, `PATCH` (partial update) and `DELETE` (204) `/api/v1/app/{app_id}/endpoint/{endpoint_id}` take the endpoint's id or its uid, and `{app_id}` takes the application's id or uid.
- **SV3** (verified, [source](https://api.svix.com/api/v1/openapi.json)): A uid is 1–256 characters of letters, digits, `-`, `_` and `.`, unique among the application's endpoints, so it names the endpoint for every later request and a create whose answer was lost is found by it.
- **SV4** (verified, [source](https://api.svix.com/api/v1/openapi.json)): The endpoint's signing secret is generated when `secret` is null (recommended) and is readable at any time with `GET …/endpoint/{endpoint_id}/secret` (`{ key }`): it is not a once-only value, and this recipe does not output it (an endpoint answer does not carry it).
- **SV5** (verified, [source](https://api.svix.com/api/v1/openapi.json)): The API is served per region (`api.us.svix.com`, `api.eu.svix.com`, `api.ca.svix.com`, `api.au.svix.com`), and POST requests accept an `idempotency-key` header.
- **SV6** **(unverified)**: A create with a uid that exists already answers 409 (the specification lists 409 for every operation without saying when), after which the endpoint is found by its uid and claimed only if an earlier intent of the same scope named it.
- **SV7** **(unverified)**: `description` is answered as sent (default empty), `disabled` as a boolean and `eventTypes` as the list sent, so they compare without drift on every plan; accounts outside the US region set `base_url` in the provider block.
