Each file is a complete `release.plan.yaml`. Copy one to the root of your repository as `release.plan.yaml`, replace
the provider ids, and run `sponson plan`. Every example is checked by `scenarios/docs/examples.test.ts`: it must parse
and plan cleanly against the local fake cloud in every environment it declares, and validate against
[the schema](https://github.com/MishaBear94/Sponson/blob/main/schema/release.plan.schema.json).

## nextjs-neon-preview.plan.yaml

The smallest useful plan. `db` creates a Neon branch named `sponson/preview/<scope>` from `main`; `env` writes
`DATABASE_URL` (from the branch's sensitive `connection_string`), a host, a secret and a literal into the preview
target for the current git branch.

```text
$ sponson plan --pr 42
sponson plan · preview · pr-42 · plan 6fb910c2

+ db   neon.branch  create   Neon branch sponson/preview/pr-42  sponson/preview/pr-42
? env  vercel.env   pending  waiting on `db`
    + DATABASE_URL (preview, feat/checkout)  (pending ← db.connection_string)
    + DATABASE_HOST (preview, feat/checkout)  (pending ← db.host)
    + STRIPE_SECRET_KEY (preview, feat/checkout)  (secret)
    + NEXT_PUBLIC_STAGE (preview, feat/checkout)  (secret)

1 to create, 1 pending
```

Every Vercel variable is shown as `(secret)` in the diff: the adapter treats all of them as sensitive.

`env` is `pending` until `db` exists; one `apply` creates both, in that order. Closing the pull request and running
`sponson apply --destroy` deletes the variables and then the branch.

```yaml nextjs-neon-preview.plan.yaml
# yaml-language-server: $schema=https://raw.githubusercontent.com/MishaBear94/Sponson/main/schema/release.plan.schema.json
#
# A Next.js app on Vercel with a Neon Postgres database. Every pull request gets its own
# database branch, and that pull request's preview deployments get its connection string.
version: 1
providers:
  vercel: { project: prj_acme_web }   # .vercel/project.json → projectId
  neon: { project: proj_acme_db }     # Neon console → project settings → project ID

changes:
  # One Neon branch per scope. `name` defaults to sponson/<env>/<scope>, so pull request 42
  # gets `sponson/preview/pr-42`; `parent` defaults to `main`.
  - id: db
    adapter: neon
    op: branch
    parent: main
    environments: [preview]

  # Preview variables. With target preview and no `branch:`, they apply to the current git
  # branch only, so two pull requests never see each other's database.
  - id: env
    adapter: vercel
    op: env
    target: preview
    values:
      DATABASE_URL: { from: db.connection_string }             # a sensitive output: never printed, never in a receipt
      DATABASE_HOST: { from: db.host }                         # a plain output
      STRIPE_SECRET_KEY: { secret: "env://STRIPE_SECRET_KEY" } # read from the environment when Sponson runs
      NEXT_PUBLIC_STAGE: preview                               # a literal
    environments: [preview]
```

## nextjs-planetscale-preview.plan.yaml

The same shape with PlanetScale. `db` creates a development branch `sponson-preview-<scope>` from `main` and waits
until PlanetScale reports it ready; `dbpw` creates a password on it; `env` writes the password's `connection_string`
to `DATABASE_URL`. On the first plan, `dbpw` and `env` are `pending`; one `apply` creates all three, in that order.

PlanetScale shows a password's plaintext only when it is created, so `connection_string` is a
[once-only output](/reference/plan-format#once-only-outputs). `env` receives it in the run that creates the password.
On every later run, `env` keeps the value it holds: the plan shows all three lines unchanged and `apply` writes nothing.
If `DATABASE_URL` is deleted in Vercel, `env` is refused with `OUTPUT_UNAVAILABLE`, because no later run can read the
value again. Sponson does not rotate the password on its own. To get a new one, delete the password in PlanetScale:
the next `apply` creates a new password and writes its connection string. `sponson apply --destroy` deletes the
variable, then the password, then the branch.

```yaml nextjs-planetscale-preview.plan.yaml
# yaml-language-server: $schema=https://raw.githubusercontent.com/MishaBear94/Sponson/main/schema/release.plan.schema.json
#
# A Next.js app on Vercel with a PlanetScale (Vitess / MySQL) database. Every pull request gets its own
# development branch and a password on it, and that pull request's preview deployments get its connection string.
# Credentials: PLANETSCALE_SERVICE_TOKEN_ID and PLANETSCALE_SERVICE_TOKEN (a service token), VERCEL_TOKEN.
version: 1
providers:
  vercel: { project: prj_acme_web }                        # .vercel/project.json → projectId
  planetscale: { organization: acme, database: acme-db }   # https://app.planetscale.com/<organization>/<database>

changes:
  # One development branch per scope, `sponson-<env>-<scope>` (pull request 42: `sponson-preview-pr-42`),
  # from `main`. Apply waits until PlanetScale reports it ready.
  - id: db
    adapter: planetscale
    op: branch
    parent: main
    environments: [preview]

  # A password on that branch. PlanetScale shows its plaintext once, when it is created, so `connection_string`
  # is a once-only output: `env` below receives it in the same run, later runs keep what `env` holds and write
  # nothing, and Sponson never rotates the password on its own.
  - id: dbpw
    adapter: planetscale
    op: password
    branch: { from: db.name }
    role: admin
    environments: [preview]

  - id: env
    adapter: vercel
    op: env
    target: preview
    values:
      DATABASE_URL: { from: dbpw.connection_string }   # sensitive and once-only: never printed, never stored
      DATABASE_USERNAME: { from: dbpw.username }        # a plain output
      NEXT_PUBLIC_STAGE: preview
    environments: [preview]
```

## nextjs-supabase-preview.plan.yaml

The Supabase version of the plan above. `db` creates a Supabase preview branch named `sponson-preview-<scope>` on the
project (branching must be enabled on it) and waits until it is `ACTIVE_HEALTHY`; `env` writes its sensitive
`connection_string` and its `api_url` into the preview target for the current git branch; `auth_callback` puts the
preview URL on the branch's own Auth redirect allow-list, because a branch is a project with its own Auth settings.
Without `project:`, an `auth_redirect` line edits the allow-list of `providers.supabase.project` instead, leaving every
entry Sponson did not add in place.

The branch's API keys are not an output yet, so the example passes the anon key as a secret.
`sponson apply --destroy` removes the redirect, the variables, then the branch.

```yaml nextjs-supabase-preview.plan.yaml
# yaml-language-server: $schema=https://raw.githubusercontent.com/MishaBear94/Sponson/main/schema/release.plan.schema.json
#
# A Next.js app on Vercel with Supabase. Every pull request gets its own Supabase preview branch (a
# project of its own, with its own database, API URL and Auth settings); that pull request's preview
# deployments get the branch's connection string and URL, and the preview URL is allowed as an Auth
# redirect on the branch.
version: 1
providers:
  vercel: { project: prj_acme_web }                  # .vercel/project.json → projectId
  supabase: { project: acmewebprojectrefxyz }        # `supabase link` → supabase/.temp/project-ref; branching enabled

changes:
  # One preview branch per scope. `name` defaults to sponson-<env>-<scope>, so pull request 42 gets
  # `sponson-preview-pr-42`. Apply waits until the branch is up (SPONSON_SUPABASE_TIMEOUT_MS).
  - id: db
    adapter: supabase
    op: branch
    environments: [preview]

  # Preview variables for the current git branch only.
  - id: env
    adapter: vercel
    op: env
    target: preview
    values:
      DATABASE_URL: { from: db.connection_string }   # sensitive: never printed, never in a receipt
      NEXT_PUBLIC_SUPABASE_URL: { from: db.api_url } # https://<branch ref>.supabase.co
      NEXT_PUBLIC_SUPABASE_ANON_KEY: { secret: "env://SUPABASE_PREVIEW_ANON_KEY" } # the branch's keys are not an output yet
    environments: [preview]

  # The preview's URL on the branch's own Auth redirect allow-list. `project` points the line at the
  # branch; without it, the line edits the allow-list of providers.supabase.project.
  - id: auth_callback
    adapter: supabase
    op: auth_redirect
    project: { from: db.project_ref }
    url: { from: env.preview_url }
    environments: [preview]
```

## vercel-shared-and-branch-vars.plan.yaml

Three levels of Vercel variables:

- `branch: "*"` writes project-wide preview variables that every preview deployment sees.
- Without `branch:`, preview variables apply to the current git branch only.
- `target: production` writes production variables; that line is filtered to `environments: [production]`.

Project-wide variables are owned by the scope that applied them first and are destroyed with it. Apply this plan from
the default branch (scope `main`) before pull requests use it; pull request scopes then rely on the shared variables
without owning them, and a pull request that tries to change one is refused with `OWNED_BY_OTHER_SCOPE`.

```yaml vercel-shared-and-branch-vars.plan.yaml
# yaml-language-server: $schema=https://raw.githubusercontent.com/MishaBear94/Sponson/main/schema/release.plan.schema.json
#
# Vercel variables at three levels: project-wide preview variables, variables for one
# preview branch, and production variables. No database; Vercel only.
version: 1
environments: [preview, production]
providers:
  vercel: { project: prj_acme_web, team: team_acme }   # `team` only for projects owned by a team

changes:
  # Project-wide preview variables (`branch: "*"`): every preview deployment sees them,
  # whatever its git branch. They belong to the scope that first applies them; apply this
  # plan from the default branch first so that scope is `main`, which is never destroyed.
  - id: preview-shared
    adapter: vercel
    op: env
    target: preview
    branch: "*"
    values:
      NEXT_PUBLIC_API_BASE: https://api.staging.acme.dev
      SENTRY_AUTH_TOKEN: { secret: "env://SENTRY_AUTH_TOKEN" }
    environments: [preview]

  # Variables for the current git branch only (the default for target preview).
  # `${ctx.*}` is interpolated into strings before the adapter sees them.
  - id: preview-branch
    adapter: vercel
    op: env
    target: preview
    values:
      NEXT_PUBLIC_SCOPE: "${ctx.scope}"           # pr-42, branch-feat-x or main
      NEXT_PUBLIC_COMMIT: "${ctx.git.short_sha}"
    environments: [preview]

  # Production. Applying it needs `--env production --approved-by <who>`.
  - id: production
    adapter: vercel
    op: env
    target: production
    values:
      NEXT_PUBLIC_API_BASE: https://api.acme.dev
      SENTRY_AUTH_TOKEN: { secret: "env://SENTRY_AUTH_TOKEN" }
    environments: [production]
```

## clerk-preview-callbacks.plan.yaml

`callback` reads `env.preview_url`, which only exists once Vercel's deployment of this commit is `READY`. The first
`apply` creates the branch and the variables, then stops:

```text
$ sponson apply
...
? callback  clerk.redirect_allow  waiting    waiting on deploy

apply partial: waiting on deploy for lines callback
```

In `--json`, `receipt.status` is `partial` and `receipt.lines.callback` has `status: "waiting"` and
`waitingFor: "deploy"`.

Exit code 0. Run `sponson apply` again after the deploy (the README's workflow does it on `deployment_status`) and the
callback is registered. With `--wait`, one `apply` polls until the deploy finishes instead. If the deploy fails, the
callback is `skipped` with `EXTERNAL_FAILED` and the branch and variables stay.

```yaml clerk-preview-callbacks.plan.yaml
# yaml-language-server: $schema=https://raw.githubusercontent.com/MishaBear94/Sponson/main/schema/release.plan.schema.json
#
# Each preview deployment's URL is allowed as a Clerk redirect URL. The URL exists only
# after Vercel has deployed, so the first `apply` stops with status `partial` and the
# callback line `waiting` for the deploy. The next `apply` (for example from a
# `deployment_status` workflow) finishes it. Same command, no flags.
version: 1
providers:
  vercel: { project: prj_acme_web }
  neon: { project: proj_acme_db }

changes:
  - id: db
    adapter: neon
    op: branch
    environments: [preview]

  # vercel.env declares `preview_url` and `deployment_id` as outputs that become available
  # only after the deploy of this commit is READY.
  - id: env
    adapter: vercel
    op: env
    target: preview
    values:
      DATABASE_URL: { from: db.connection_string }
      CLERK_SECRET_KEY: { secret: "env://CLERK_PREVIEW_SECRET_KEY" }
    environments: [preview]

  # Reads an external output, so it waits for the deploy. A `from:` reference is the
  # whole value; it cannot be combined with other text.
  - id: callback
    adapter: clerk
    op: redirect_allow
    url: { from: env.preview_url }
    environments: [preview]
```

## launchdarkly-preview-flags.plan.yaml

Two individual targets on flags that already exist in the LaunchDarkly project `acme-web`, environment `preview`.
`checkout` serves `new-checkout` = `true` to the context of kind `url` whose key is the preview URL, so like the Clerk
callback above it waits for the deploy; `pricing` serves the variation named `Treatment` of `pricing-page` to the user
key `pr-42` (the scope) and is applied at once. `apply --destroy` removes exactly these two targets; the flags, their
rules and everyone else's targets stay. A target moved to another variation in the LaunchDarkly console is `changed`
drift, refused until `--reconcile`.

```yaml launchdarkly-preview-flags.plan.yaml
# yaml-language-server: $schema=https://raw.githubusercontent.com/MishaBear94/Sponson/main/schema/release.plan.schema.json
#
# Feature flags turned on for each pull request's preview, and off again when it closes
# (`sponson apply --destroy`). Sponson adds individual targets to flags that already exist
# in LaunchDarkly; it never creates, deletes, or switches flags. LAUNCHDARKLY_ACCESS_TOKEN
# is read from the environment.
version: 1
providers:
  vercel: { project: prj_acme_web }
  # A project key and an environment key. Use a preview or test environment: one that
  # requires approvals for flag changes refuses Sponson's writes.
  launchdarkly: { project: acme-web, environment: preview }

changes:
  - id: env
    adapter: vercel
    op: env
    target: preview
    values:
      LAUNCHDARKLY_CLIENT_SIDE_ID: { secret: "env://LAUNCHDARKLY_PREVIEW_CLIENT_SIDE_ID" }
    environments: [preview]

  # The new checkout, served `true` to the preview deployment. The app evaluates flags with a
  # context of kind `url` whose key is its own URL, so the target is the preview URL: it exists
  # once Vercel has deployed this commit, and the next `apply` finishes the line.
  - id: checkout
    adapter: launchdarkly
    op: flag_target
    flag: new-checkout
    context_kind: url
    key: { from: env.preview_url }
    variation: true
    environments: [preview]

  # A multivariate flag, by variation name. `key` defaults to the scope (`pr-42`) and
  # `context_kind` to `user`: the app sends the pull request as a user key in previews.
  - id: pricing
    adapter: launchdarkly
    op: flag_target
    flag: pricing-page
    variation: Treatment
    environments: [preview]
```

## explicit-deploy.plan.yaml

A `vercel.deploy` line starts the deployment after the variables are written (`depends_on: [env]`), and its
`preview_url` is available as soon as the line is applied, so one `apply` runs to the end and waits for the build (up
to `SPONSON_DEPLOY_TIMEOUT_MS`, default 120 seconds). Use it when automatic preview deployments are turned off in
Vercel; with them on, prefer the previous example.

```yaml explicit-deploy.plan.yaml
# yaml-language-server: $schema=https://raw.githubusercontent.com/MishaBear94/Sponson/main/schema/release.plan.schema.json
#
# Sponson starts the deployment itself, after the variables are written, so nothing waits on
# an external event and one `apply` runs to the end. Use this when automatic preview
# deployments are turned off in Vercel; otherwise prefer clerk-preview-callbacks.plan.yaml.
version: 1
providers:
  vercel: { project: prj_acme_web }

changes:
  - id: env
    adapter: vercel
    op: env
    target: preview
    values:
      FEATURE_FLAGS: "checkout-v2,search-v3"
    environments: [preview]

  # No data flows from `env` to `deploy`, but the deploy must come after the variables:
  # `depends_on` orders lines without a reference. The deploy's `preview_url` is an
  # immediate output: `apply` waits for the build (SPONSON_DEPLOY_TIMEOUT_MS, default 120 s).
  - id: deploy
    adapter: vercel
    op: deploy
    depends_on: [env]
    environments: [preview]

  - id: callback
    adapter: clerk
    op: redirect_allow
    url: { from: deploy.preview_url }
    environments: [preview]
```

## production-with-approval.plan.yaml

Preview lines use a per-PR database; the production line takes its values from secrets. Applying production:

```bash
sponson plan  --env production              # read-only; reports requiresApproval: true
sponson apply --env production              # refused: ENV_NOT_APPROVED (exit 2), nothing written
sponson apply --env production --approved-by alice
```

`--approved-by` (or `SPONSON_APPROVED_BY`) should come from a person or an approval workflow, never from an agent.
The approver is recorded in the receipt as `approvedBy`.

```yaml production-with-approval.plan.yaml
# yaml-language-server: $schema=https://raw.githubusercontent.com/MishaBear94/Sponson/main/schema/release.plan.schema.json
#
# Preview and production in one file. Lines are filtered by `environments:`; `--env` picks
# the environment (default preview; production is never inferred from a branch name).
# Any run that writes to production is refused with ENV_NOT_APPROVED unless an approver
# is named: `sponson apply --env production --approved-by alice`.
version: 1
environments: [preview, production]
providers:
  vercel: { project: prj_acme_web }
  neon: { project: proj_acme_db }

changes:
  - id: db
    adapter: neon
    op: branch
    environments: [preview]

  - id: env-preview
    adapter: vercel
    op: env
    target: preview
    values:
      DATABASE_URL: { from: db.connection_string }
      STRIPE_SECRET_KEY: { secret: "env://STRIPE_TEST_SECRET_KEY" }
    environments: [preview]

  # Production values come from secrets, never from another line: there is no per-PR
  # database in production. Without `environments: [production]`, this line would also run
  # in preview, and every preview run would then need approval because it writes to production.
  - id: env-production
    adapter: vercel
    op: env
    target: production
    values:
      DATABASE_URL: { secret: "env://PRODUCTION_DATABASE_URL" }
      STRIPE_SECRET_KEY: { secret: "env://STRIPE_LIVE_SECRET_KEY" }
    environments: [production]
```

## adopting-an-existing-project.plan.yaml

What `sponson init` appends to an existing plan when it finds resources no scope manages: variables become
`{ keep: true }`, grouped by target and git branch; an existing Neon branch is adopted by its `name:`. Nothing live
changes, and adopted resources are never destroyed. Run `sponson init --adopt <key>` to adopt a single resource; the
keys are listed under `drift` (`kind: unmanaged`) in `sponson plan --json`.

```yaml adopting-an-existing-project.plan.yaml
# yaml-language-server: $schema=https://raw.githubusercontent.com/MishaBear94/Sponson/main/schema/release.plan.schema.json
#
# A project that existed before Sponson. These lines are what `sponson init` appends when it
# adopts unmanaged resources: values are never copied into the plan, only `{ keep: true }`
# ("whatever is live"). Adopted resources are never destroyed by `apply --destroy`.
version: 1
environments: [preview, production]
providers:
  vercel: { project: prj_acme_web }
  neon: { project: proj_acme_db }

changes:
  # Project-wide preview variables someone set in the dashboard. Sponson now tracks that they
  # exist and reports drift; it does not manage their values. A `_KEY` name may be `{ keep: true }`:
  # only literal strings and numbers are refused for secret-looking names.
  - id: env-preview-shared
    adapter: vercel
    op: env
    target: preview
    branch: "*"
    values:
      SENTRY_DSN: { keep: true }
      NEXT_PUBLIC_POSTHOG_KEY: { keep: true }
    environments: [preview]

  - id: env-production
    adapter: vercel
    op: env
    target: production
    values:
      DATABASE_URL: { keep: true }
    environments: [production]

  # An existing Neon branch, identified by its name.
  - id: db-staging
    adapter: neon
    op: branch
    name: staging
    environments: [preview]

  # To let Sponson manage a value, replace `{ keep: true }` with a literal or a reference,
  # for example `SENTRY_DSN: { secret: "env://SENTRY_DSN" }`.
```

## http-flags-webhooks-allowlists.plan.yaml

**Illustrative.** The generic `http` adapter managing what has no Sponson adapter: a feature gate per pull request
(`http.resource`, located by name), a test-mode webhook endpoint (form-encoded, with an idempotency key and a
sensitive output), the preview URL on an application's allowed web origins (`http.list_item`, an item of a JSON
array), and a callback on a comma-separated redirect allow-list (`shape: delimited`). Each API is a block under
`providers.http` naming its credential's environment variable. The endpoints follow the providers' published API
references as we understand them; plan against the real API (`sponson plan` only reads) before the first apply.
`apply --destroy` removes the gate, the endpoint and the two list items, and leaves every other origin and
redirect as it was. Reference: [`http.resource`](/reference/plan-format#http-resource),
[`http.list_item`](/reference/plan-format#http-list_item).

```yaml http-flags-webhooks-allowlists.plan.yaml
# yaml-language-server: $schema=../schema/release.plan.schema.json
#
# ILLUSTRATIVE. The generic `http` adapter driving four SaaS APIs that have no Sponson adapter of their own. The
# endpoints, envelopes and credential headers follow each provider's published API reference as we understand it;
# check them against the current docs before relying on this plan, and run `sponson plan` first: it only reads.
# The ids (Auth0 client, Supabase project ref, tenant domain) are placeholders.
#
# Each `base_url_env` is an optional override of `base_url` (a staging API; the test suite points them at the
# local fake cloud). Credentials are environment variable NAMES; Sponson never stores or prints their values.
version: 1
environments: [preview]
providers:
  vercel: { project: prj_acme_web }
  http:
    statsig:
      base_url: https://statsigapi.net/console/v1
      base_url_env: STATSIG_API_URL
      auth: { header: STATSIG-API-KEY, value_env: STATSIG_CONSOLE_KEY }
    stripe:
      base_url: https://api.stripe.com/v1
      base_url_env: STRIPE_API_URL
      auth: { bearer_env: STRIPE_TEST_SECRET_KEY }
      encoding: form
    auth0:
      base_url: https://acme.us.auth0.com/api/v2
      base_url_env: AUTH0_API_URL
      auth: { bearer_env: AUTH0_MANAGEMENT_TOKEN }
    supabase:
      base_url: https://api.supabase.com/v1
      base_url_env: SUPABASE_API_URL
      auth: { bearer_env: SUPABASE_ACCESS_TOKEN }
changes:
  # The preview deployment; its URL exists once Vercel's build of this commit is ready.
  - id: web
    adapter: vercel
    op: env
    target: preview
    values:
```
